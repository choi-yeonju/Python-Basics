## 1. #01 준비작업 — 왜 체크포인트가 여러 개인가

### 개념
"체크포인트"는 전처리 파이프라인(라벨링 → 더미 → 로그변환 → 이상치대체 → VIF제거 → 스케일링)이 **한 단계씩 누적된 스냅샷**이다. 체크포인트 0(기준선)부터 4(전체 전처리 완료)까지 있고, 전처리를 더 할수록 "통계적으로 더 나은 모델"이 되는 게 보장되지 않기 때문에 **각 단계마다 모델을 실제로 적합해보고 성능을 비교**해야 한다. 이게 이 실습 전체의 존재 이유다.

### 유의할 점 — 종속변수 척도가 체크포인트마다 다르다
```python
medv_scale = DataFrame()
for name in checkpoints:
    medv_scale[name] = checkpoints[name][target].describe()
```
체크포인트 1부터 종속변수(MEDV)에 `log1p` 변환이 들어가 있어서, **원본 달러 단위(0_기준선)와 로그 단위(1~4)의 척도가 다르다.** 이걸 확인 안 하고 R²나 AIC를 그냥 비교하면 잘못된 결론이 나온다. → 이게 다음 섹션의 핵심 함정으로 이어진다.

## 2. #02 체크포인트별 모델 적합 및 성능 비교

### 2-1. 성능지표 개념 정리 (말로 풀어서)

| 지표 | 뜻 | 특징 |
|---|---|---|
| **R²(결정계수)** | 종속변수의 전체 변동(분산) 중에서 모형이 설명해내는 비율. "이 모델이 Y의 움직임을 몇 %나 설명하는가" | 0~1, 1에 가까울수록 설명력 좋음. 독립변수를 추가하면 의미 없는 변수라도 R²는 절대 줄지 않고 늘거나 그대로다 → 그래서 변수 많은 모델이 유리해 보이는 착시가 생김 |
| **Adj.R²(수정된 결정계수)** | R²에 변수 개수 페널티를 적용해서 보정한 값 | 불필요한 변수를 추가하면 오히려 값이 떨어질 수 있음 → 변수 개수가 다른 모델끼리 비교할 때 R²보다 신뢰할 수 있음 |
| **AIC / BIC** | 모형의 "적합도"와 "복잡도(변수 수)"를 동시에 고려하는 정보기준 | **작을수록 좋은 모형.** BIC가 AIC보다 변수 수 증가에 더 강한 페널티를 줌. **단, 종속변수의 척도(단위)가 같은 모형끼리만 비교 가능** |
| **RMSE (평균제곱근오차)** | 예측값과 실제값 차이를 제곱해서 평균낸 뒤 다시 제곱근을 취한 값 | 원래 단위(예: 천 달러)로 나오기 때문에 "평균적으로 몇 단위 정도 틀리는가"를 직관적으로 보여줌. **오늘 실습의 최종 채택 기준 1순위** |
| **MAE (평균절대오차)** | 예측값과 실제값 차이의 절댓값을 평균낸 값 | RMSE보다 이상치(큰 오차)에 덜 민감함 |

### 2-2. 오늘의 핵심 함정 — "모델 척도" vs "원본 척도"

```python
# 로그변환이 적용된 체크포인트라면 예측값/실제값을 원래 단위로 되돌린다
if log:
    y_true = np.expm1(data[target])       # 종속변수 역변환 (로그→원래단위)
    y_pred = np.expm1(fit.fittedvalues)   # 예측값도 동일하게 역변환
else:
    y_true = data[target]                 # 체크포인트 0은 이미 원본 척도
    y_pred = fit.fittedvalues
```

- `fit.rsquared`, `fit.aic`, `fit.bic`는 **모델이 실제로 학습한 척도(로그 단위)** 에서 계산된 값이다. → 로그를 쓴 모델과 안 쓴 모델끼리는 **절대 비교 불가.**
- 반면 `r2_score(y_true, y_pred)`, `RMSE`, `MAE`는 **역변환(np.expm1) 후 원본 달러 단위**에서 다시 계산하기 때문에 체크포인트 간 **공정 비교가 가능**하다.
- `np.expm1(x)` = `exp(x) - 1`. 앞서 `log1p(x)` = `log(1+x)`로 변환했던 것의 정확한 역함수다. (log1p를 쓰는 이유: x=0 근처 값도 안전하게 로그 변환하기 위해서 — `log(0)`은 정의되지 않지만 `log1p(0)=log(1)=0`은 계산됨)

### 2-3. 최종모델 채택 기준
```
1순위: 원본 척도 RMSE (작을수록 좋음, 실제 예측오차 크기)
2순위: 간명성 (Parsimony) — RMSE가 비슷하면 변수 개수가 적은 쪽 선택
```
"성능 좋은 모델"이 항상 "변수 제일 많이 넣은 모델"이 아니라는 것, 그리고 **비교 가능한 척도로 통일**하는 게 먼저라는 것 — 이 두 가지가 이 섹션의 결론이다.

### 2-4. 후진소거법(Backward Elimination) 복습
```python
fit = my_ols.auto_ols(data, target, log1p_y=log, log_x=log_x, log1p_x=log1p_x,
                       reflect_x=reflect_x, backward=True, report=False, test=False)
```
동작 원리(`auto_ols` 내부 while 루프):
1. 모든 독립변수를 넣고 OLS 적합
2. 등분산성(Breusch-Pagan) 확인 → 등분산 위배면 이후 유의성 판정을 HC3 강건표준오차 기준으로
3. 유의확률이 **가장 큰(=가장 유의하지 않은) 변수 딱 1개만** 제거
4. 재적합 → 모든 변수가 유의(p<0.05)해지거나 변수가 1개만 남을 때까지 반복

**왜 한 번에 하나씩만 제거하는가?** 독립변수끼리 상관관계(다중공선성)가 있으면, 유의하지 않아 보이는 변수를 지우고 재적합했을 때 원래는 유의했을 다른 변수의 유의확률이 바뀔 수 있다. 여러 개를 한꺼번에 지우면 이 상호작용을 놓치고 원래 유의했을 변수까지 함께 날려버릴 위험이 있다.

## 3. #03 최종 모델 분석 결과 보고

### 3-1. 모형 적합도 문장 (`report_fitness`)
```python
my_ols.report_fitness(final_fit, log1p_y=True, log_x=log_x, log1p_x=log1p_x, reflect_x=reflect_x)
```
APA(학술논문) 스타일 문장을 자동 생성:
> `F(df_model, df_resid) = ..., p ..., R² = ..., Adj.R² = ..., Durbin-Watson = ...`

여기서 F-검정이 뭘 검정하는지 말로 풀면:
- **귀무가설(H0)**: "이 회귀모형에 포함된 독립변수들은 종속변수를 설명하는 데 전혀 도움이 안 된다 (모든 회귀계수가 0이다)"
- **대립가설(H1)**: "적어도 하나의 독립변수는 종속변수를 유의하게 설명한다"
- p < .05면 대립가설 채택 → "이 모형은 통계적으로 유의하다"고 말할 수 있는 근거가 생김

### 3-2. 계수 보고표 (`report_variables`)
독립변수마다 B(비표준화계수), 표준오차, 베타(표준화계수), t, 유의확률, 공차, VIF를 정리한다.

- **표준화계수(베타)**: `B × (독립변수 표준편차 / 종속변수 표준편차)`. 원래 단위가 서로 다른 변수들(예: 방 개수 vs 범죄율)의 영향력 크기를 **같은 기준(표준편차 단위)** 으로 맞춰서 "어떤 변수가 상대적으로 더 큰 영향을 미치는가"를 비교할 수 있게 해준다. B는 단위가 달라서 직접 비교가 불가능하지만 베타는 가능하다.
- **공차(Tolerance)** = `1/VIF`. VIF(분산팽창계수)가 클수록 그 변수는 다른 독립변수들과 상관관계가 높다(다중공선성)는 뜻. 공차가 작을수록(=VIF가 클수록) 위험 신호.
- **HC3 로버스트 표준오차**: 등분산성 가정이 깨졌을 때(이분산 존재) 일반 OLS의 표준오차는 신뢰할 수 없다. HC3는 이분산에 강건하게 표준오차를 다시 계산하는 방법. **회귀계수 B 자체는 그대로**고, 표준오차·t값·유의확률만 바뀐다(t = B / 표준오차이므로 표준오차가 바뀌면 t와 p도 같이 바뀜).

### 3-3. 영향력 순위 시각화 (`plot_beta`)
표준화계수(베타)의 절댓값 기준으로 가로 막대 그래프. 부호(+/-)로 색을 구분해서 "어떤 변수가 종속변수를 얼마나, 어느 방향으로 움직이는가"를 한눈에 보여준다.

### 3-4. 회귀계수 해석 문장 — 로그/로그1p/반사변환 해석 공식 (중요!)

변환 종류에 따라 계수 B를 "% 증감"으로 해석하는 방식이 완전히 다르다. 이건 면접에서도 자주 나오는 포인트라 개념적으로 정리해둔다.

| X 변환 | Y 변환 | 계수 B의 의미 | 해석 예시 |
|---|---|---|---|
| 없음 | 없음 | X가 1 증가할 때 Y가 B만큼 (절대량) 변화 | "방 개수가 1개 늘 때 집값이 B천 달러 변화" |
| log | 없음 | X가 1% 증가할 때 Y가 약 `B×ln(1.01)` 만큼 (절대량) 변화 | 근사 공식 |
| 없음 | log(1p) | X가 1 증가할 때 Y가 약 `(e^B − 1)×100`% 변화 | "X가 1 늘면 Y가 약 …% 증가" |
| log | log(1p) | **탄력성(elasticity)**: X가 1% 증가할 때 Y가 약 B% 변화 | 경제학에서 말하는 탄력성과 동일한 개념 |

- `log1p` 변환된 변수는 "변수 자체"가 아니라 **"(1+변수)"** 를 기준으로 % 해석해야 한다 (값이 0 근처일 때는 이 근사가 부정확해짐).
- **반사(reflect) 변환** `log1p(max - x)`는 대소 관계 자체를 뒤집는 변환이다. 그래서 반사된 변수가 홀수 개면(x만 반사, 또는 y만 반사) 문장의 방향(증가/감소)이 "반사값 기준"과 "원래 변수 기준"이 서로 반대가 된다. 이 코드는 그 방향을 자동으로 다시 뒤집어서 원 변수 기준 해설을 괄호로 덧붙여준다.
- 반사변환을 언제 쓰나: 왼쪽으로 심하게 치우친(좌측 꼬리가 긴) 분포를 로그변환으로 정규화하고 싶을 때, 값을 뒤집어서 로그변환이 잘 먹히는 형태로 바꾸는 트릭.

## 4. #04 최종 모델의 회귀분석 가정 검정 4종

> 회귀분석이 통계적으로 신뢰할 수 있으려면 **잔차(실제값-예측값)** 가 만족해야 하는 4가지 가정이 있다. 이 4가지는 항상 **선형성 → 정규성 → 등분산성 → 독립성** 순서로 검정한다 (`auto_ols`의 test 블록도 이 순서로 고정되어 있음).

### 4-1. 선형성 검정 — Ramsey RESET Test

**개념**: 지금 적합한 모형이 "직선(또는 초평면) 관계"로 충분히 설명되는지, 아니면 곡선 관계가 남아있는지를 확인한다. 방법은 기존 모형의 예측값을 제곱한 항(고차항, power=2)을 추가로 넣어봤을 때 그 항이 유의미한 설명력을 갖는지 F검정으로 본다.

**가설을 말로 풀면**:
- 귀무가설(H0): "기존의 직선 모형에 고차항을 추가해도 설명력이 유의하게 늘지 않는다" → 즉 지금 모델(직선)로 충분하다, 선형성 가정을 위배한다고 볼 근거가 없다
- 대립가설(H1): "고차항을 추가하니 설명력이 유의하게 늘었다" → 직선으로는 못 잡아낸 곡선 관계가 남아있다, 선형성 위배

**판정**: p ≥ 0.05 → 귀무가설 채택(선형성 만족) / p < 0.05 → 대립가설 채택(선형성 위배)

```python
my_ols.test_linear(final_fit, plot=True, title="적합값 대비 잔차 (lowess 추세선)")
```
시각화: x축 적합값(예측값), y축 잔차. 잔차가 0을 중심으로 뚜렷한 패턴(곡선) 없이 무작위로 흩어져 있어야 선형성 가정에 부합. lowess(국소회귀) 추세선이 0 근처에서 평평하면 OK, 휘어있으면 문제.

### 4-2. 정규성 검정 — Shapiro-Wilk / Kolmogorov-Smirnov + Q-Q Plot + 68-95-99.7 규칙

**개념**: 잔차가 정규분포를 따라야 t검정·F검정 등에서 산출한 p-value를 신뢰할 수 있다.

**가설을 말로 풀면**:
- 귀무가설(H0): "잔차의 분포는 정규분포와 차이가 없다"
- 대립가설(H1): "잔차의 분포는 정규분포와 유의하게 다르다"

**검정 방법 선택 기준**: 표본수(n) < 30이면 Shapiro-Wilk, n ≥ 30이면 Kolmogorov-Smirnov(K-S) 검정을 사용한다. (Shapiro-Wilk는 소표본에 강하고, K-S는 표본을 표준화한 뒤 표준정규분포와 비교하는 방식.)

**세 가지 증거를 함께 본다**:
1. 통계량 + p-value (위 가설 판정)
2. **Q-Q Plot**: 잔차를 표준화(z-score)한 뒤, 이론적 정규분포 분위수와 실제 표본 분위수를 산점도로 비교. 점들이 대각선(y=x)에 가까이 붙어있을수록 정규성에 가까움.
3. **68-95-99.7 규칙(경험적 규칙)**: 정규분포라면 평균 ± 1×표준편차 안에 약 68%, ±2×표준편차 안에 약 95%, ±3×표준편차 안에 약 99.7%의 데이터가 들어가야 한다. 여기서는 표준편차 대신 **루트MSE(잔차의 표준편차 추정치)** 를 기준으로 실제 포함 비율을 계산하고, 기대 비율에서 ±2SE(표준오차) 허용범위 안에 드는지로 판정한다.

```python
my_ols.test_normal(final_fit, plot=True)
```

### 4-3. 등분산성 검정 — Breusch-Pagan Test

**개념**: 잔차의 분산(흩어진 정도)이 독립변수 값과 무관하게 일정해야 한다는 가정. 예를 들어 예측값이 커질수록 잔차도 같이 커지는 "나팔 모양(부채꼴)" 패턴이 보이면 이 가정이 깨진 것(이분산성).

**가설을 말로 풀면**:
- 귀무가설(H0): "잔차의 분산은 독립변수 값에 관계없이 일정하다" (등분산성 만족)
- 대립가설(H1): "잔차의 분산이 독립변수 값에 따라 달라진다" (이분산성 존재)

```python
my_ols.test_equalvar(final_fit)
```
**판정**: F p-value < 0.05 → 대립가설 채택 → 등분산 아님 (이분산 존재)

**등분산성이 깨졌을 때의 대응**: 계수(B) 추정치 자체는 여전히 유효하지만, 표준오차·t·p-value가 왜곡될 수 있다. 그래서 **HC3 로버스트 표준오차**로 바꿔서 유의성을 다시 판단한다 (3-2 참고). 오늘 실습 결과에서도 최종모델은 등분산 가정 위배 → HC3 사용.

### 4-4. 독립성 검정 — Durbin-Watson

**개념**: 잔차들끼리 서로 독립적이어야 한다(자기상관이 없어야 한다)는 가정. 원래는 시계열 데이터(시간 순서가 있는 데이터)에서 "어제의 오차가 오늘의 오차에 영향을 주는가"를 확인하기 위한 검정이라, **시간 순서가 없는 횡단면 데이터(오늘 실습의 boston, insurance처럼)에서는 이 가정이 위배되더라도 크게 개의치 않는 경우가 많다.**

**판정 기준**: Durbin-Watson 통계량은 0~4 사이 값이며 2에 가까울수록 독립성을 만족한다고 본다.
- 1.5 ≤ DW ≤ 2.5 → 독립성 만족
- DW < 1.5 → 양(+)의 자기상관 (독립성 위반)
- DW > 2.5 → 음(-)의 자기상관 (독립성 위반)

```python
my_ols.test_independent(final_fit)
```
(다른 3개와 달리 시각화가 필요 없는 검정이라 `plot` 파라미터가 없다는 것도 코드 설계상 포인트.)

## 5. 모듈을 불러와서 쓰는 것 — 어떻게 사고해야 하는가

### 5-1. 지금 이 실습의 import 구조
```python
from jussam import load_data     # 강의용 데이터 로더 (외부 배포 패키지)
from helpers import *            # 내가/우리 팀이 계속 확장해온 자체 패키지
```
`helpers` 패키지 안에서 `my_ols.py`는 다시 상대경로로 다른 모듈을 불러온다:
```python
from . import my_plot     # 그래프 그리기 전담 (init/show/lmplot/barplot 등)
from . import my_stats    # 통계 계산 전담 (compute_vif 등)
```

**이렇게 사고하면 된다** — 하나의 거대한 파일에 다 때려박지 않고, **역할별로 모듈을 쪼갠다**:
- `my_stats.py` : 순수 통계 계산(숫자만 리턴)
- `my_plot.py` : 시각화 전담(그래프 스타일 통일)
- `my_ols.py` : 회귀분석 워크플로우 전담 — 위 두 모듈을 "조립"만 함
- `my_qtcheck.py`, `my_prep.py` : 데이터 품질확인/전처리 전담

이렇게 나눠두면 **"내가 지금 무슨 문제를 풀고 있나"에 따라 어느 모듈을 열어야 할지 바로 감이 온다.** 예를 들어 그래프 색이 이상하면 → `my_plot.py`만 보면 되고, VIF 계산이 이상하면 → `my_stats.py`만 보면 된다. `my_ols.py`는 로직 자체보다는 "어떤 순서로, 어떤 함수를 호출하는가"의 조립도라고 보면 됨.

### 5-2. 확장할 때의 원칙
- 새 기능이 필요하면: (1) 이게 순수 계산인지 시각화인지 워크플로우 조립인지 먼저 구분 → (2) 해당 모듈에만 추가 → (3) `__init__.py`에서 노출 여부 결정
- 함수 하나가 여러 일을 다 하게 만들지 말고, `test_linear`, `test_normal`, `test_equalvar`, `test_independent`처럼 **검정 하나당 함수 하나**로 쪼개서, `auto_ols`처럼 상위 함수가 그것들을 순서대로 호출하는 구조를 유지한다. → 나중에 검정 하나만 따로 쓰고 싶을 때도 재사용 가능.
- Jupyter에서 모듈 코드를 수정했으면 `importlib.reload()`로 다시 불러와야 반영된다 (지금까지 계속 써온 워크플로우).

### 5-3. "직접 소스에 코딩" vs "모듈 불러와서 코딩" — 두 버전을 왜 나누는가
- **직접 코딩 버전**: `statsmodels`의 `OLS`, `add_constant`, `het_breuschpagan` 같은 저수준 함수를 그 자리에서 직접 호출. 원리를 이해하고 있는지, 각 함수가 정확히 뭘 계산하는지 검증할 때 필요.
- **모듈 버전**(`my_ols.auto_ols`, `my_ols.report_fitness` 등): 저수준 로직을 함수 안에 캡슐화해서, 실제 분석 실무에서는 몇 줄로 전체 워크플로우(적합→후진소거→보고→검정)를 끝낼 수 있게 만든 것.

**두 버전을 나누는 이유는 "검증"이다.** 모듈로 만들기 전에 직접 코딩해서 결과가 같은지 대조해봐야, 모듈 내부에 버그가 있는지 없는지 확인할 수 있다(실제로 지난 실습에서 `my_ols.py`의 68-95-99.7 규칙 계산 버그, `test_normal`이 `test_linear` 안에 잘못 중첩된 버그 등을 이렇게 찾아냈었음). **"처음부터 끝까지 다 코딩"이 아니라 "모듈이 제대로 작동하는지 확인하는 절차"라는 게 핵심.**

## 6. 다른 데이터셋에 적용할 때 재사용 체크리스트

오늘 insurance 데이터셋 연습문제에서 boston과 똑같은 순서를 그대로 반복한 것처럼, 새 데이터셋을 만나면 아래 순서를 그대로 따라가면 된다.

1. **체크포인트 로드 & 종속변수 척도 확인** — `describe()`로 체크포인트별 종속변수 통계량 비교, 로그변환이 어디서부터 들어갔는지 파악
2. **어떤 독립변수에 log/log1p/reflect가 적용됐는지 딕셔너리로 정리** (`log_x`, `log1p_x`, `reflect_x`) — 이게 있어야 나중에 보고서 함수들이 올바른 해석 문장을 만들어줌
3. **체크포인트마다 `auto_ols(backward=True)`로 모델 적합** → `fits` 딕셔너리에 저장
4. **성능 비교표 작성 시 반드시 원본 척도로 역변환 후 비교** (`np.expm1`, `r2_score`, `RMSE`, `MAE`) — 로그 썼는지 여부가 체크포인트마다 다르면 이 단계를 절대 건너뛰면 안 됨
5. **RMSE(원본척도) 1순위, 간명성 2순위로 최종모델 채택**
6. **최종모델 보고서 4종 세트**: `report_fitness` → `report_variables` → `plot_beta` → `report_variables_text`
7. **가정검정 4종 세트 고정 순서**: `test_linear` → `test_normal` → `test_equalvar` → `test_independent`
8. 등분산성 위배 시 `hc3=final_fit.use_hc3_`를 계수 보고 함수들에 일관되게 넘겨주기 — `auto_ols`가 이미 판단해서 `fit.use_hc3_` 속성에 저장해두므로 밖에서 다시 검정할 필요 없음

## 7. 복습할 때 이것만은 확실히 — 우선순위

말로 설명할 수 있어야 하는 것 (면접 대비 포함):

1. **왜 로그 변환된 모델의 R²/AIC/BIC는 다른 척도 모델과 못 비교하는지** — "척도가 다르면 같은 지표라도 단위가 다른 걸 비교하는 셈이라서"라고 설명할 수 있어야 함
2. **4가지 가정검정 각각의 귀무가설/대립가설을 자기 말로** — 이 문서 4장의 표현을 자기 언어로 다시 말해보기
3. **표준화계수(베타)를 왜 쓰는지** — "단위가 다른 변수들의 영향력을 공정하게 비교하려고"
4. **후진소거법에서 왜 한 번에 하나씩만 지우는지** — 다중공선성 때문에 변수 간 상호작용이 있어서
5. **HC3는 뭘 바꾸고 뭘 안 바꾸는지** — 계수(B)는 그대로, 표준오차·t·p만 보정
6. **log/log1p/반사변환에 따라 계수 해석 공식이 왜 다른지** — 원본량 vs 비율(%) vs 탄력성 개념 구분
7. 소스코드 자체보다는 **"이 함수가 왜 이 순서로 호출되는가"** 를 설명할 수 있는 게 더 중요함 (실무에서는 이미 만들어진 모듈을 갖다 쓰는 경우가 많으므로, "이 워크플로우가 왜 이렇게 설계됐는가"를 이해하고 있는 게 실전 가치가 큼)
