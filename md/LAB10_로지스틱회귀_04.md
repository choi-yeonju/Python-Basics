로지스틱 회귀는 **"확률"**을 뱉는다. 근데 우리가 진짜 알고 싶은 건 "이 모형이 실제로 얼마나 잘 맞히는가"다.

## 1. 분석 순서 (오늘 노트북이 실제로 진행된 흐름)

```
1) 전처리 완료된 데이터 로드 (load_data)
   ↓
2) 로지스틱 회귀 모델 적합 (my_logit.auto_logit)
   ↓
3) 혼동행렬 만들기
   3-1) 실제 정답 꺼내기        fit.model.endog
   3-2) 예측 확률 꺼내기        fit.predict()
   3-3) 확률을 0/1로 자르기      proba > threshold
   3-4) confusion_matrix()로 2x2표 생성
   3-5) tn, fp, fn, tp = cm.ravel() 로 4칸 분해
   ↓
4) 4칸으로부터 지표 계산
   정확도 → (정확도의 함정 확인) → 정밀도/재현율 → F1
   ↓
5) 임계값을 바꿔가며 지표가 어떻게 움직이는지 실험 (0.3~0.7)

   ↓
7) 진단오즈비(DOR) — 혼동행렬 버전의 "오즈비"
   ↓
8) 지금까지 직접 짠 코드를 모듈 함수로 검증
   (plot_confusion / plot_roc / report_performance)
```

이 순서 자체가 재사용 패턴이다. 새 데이터셋을 만나도 이 8단계 그대로 따라가면 된다.

## 2. 핵심 개념 — 말로 풀어서 이해하기

### 2-1. 혼동행렬(Confusion Matrix)이 뭔가

모형이 내놓은 예측과 실제 정답을 교차해서 세어놓은 표다. **행(row) = 실제값, 열(column) = 예측값**이라는 배치가 관례다 — 이걸 헷갈리면 뒤에 나오는 지표들도 다 헷갈린다.

2x2표이므로 칸은 4개, 이름은 "실제-예측" 조합으로 정해진다:

| | 예측 0 | 예측 1 |
|---|---|---|
| **실제 0** | TN (True Negative) | FP (False Positive) |
| **실제 1** | FN (False Negative) | TP (True Positive) |

말로 풀면:
- **TN**: 실제로 음성(정상)인데, 모형도 음성이라고 맞힘
- **FP**: 실제로 음성인데, 모형이 양성이라고 헛짚음 (= 1종 오류, "가짜 경보")
- **FN**: 실제로 양성(당뇨/합격 등)인데, 모형이 음성이라고 놓침 (= 2종 오류, "진짜를 놓침")
- **TP**: 실제로 양성인데, 모형도 양성이라고 맞힘

**`cm.ravel()`이 왜 항상 `[TN, FP, FN, TP]` 순서로 나오는가**: `confusion_matrix()`가 반환하는 배열은 `[[TN, FP], [FN, TP]]` 형태의 2차원 배열이다. `.ravel()`은 이 배열을 1차원으로 평탄화(flatten)하는데, numpy는 기본적으로 **row-major(행 우선, C-order)** 순서로 펼친다. 즉 1행(TN, FP)을 먼저 다 펼치고 그다음 2행(FN, TP)을 펼치기 때문에 `TN, FP, FN, TP` 순서가 나오는 것이다. 이건 암기가 아니라 "왜 이 순서인지" 설명할 수 있어야 진짜 아는 것이다.

### 2-2. 왜 확률을 그대로 못 쓰고 임계값(threshold)으로 자르는가

로지스틱 회귀의 예측값(`fit.predict()`)은 0/1이 아니라 **"사건이 일어날 확률"**이다 (0~1 사이 실수). 그런데 실제 정답은 0 또는 1이라는 딱 떨어지는 범주다. 이 둘을 비교하려면 확률을 범주로 바꾸는 기준이 필요한데, 그게 **임계값(threshold)**이다. 관례적으로 0.5를 쓰지만(50% 넘으면 양성), 이건 정해진 규칙이 아니라 **분석자가 목적에 맞게 고르는 값**이다. (→ 5번 섹션에서 이 값을 왜/어떻게 바꾸는지 다룸)

### 2-3. 정확도(Accuracy) — 그리고 그 함정

$$\text{Accuracy} = \frac{TP+TN}{TP+TN+FP+FN}$$

말로: 전체 판정 중에서 맞게 판정한 비율. 가장 직관적이지만 **가장 잘 속는 지표**이기도 하다.

**함정**: 정답의 클래스 비율이 한쪽으로 쏠려 있으면(class imbalance), 무조건 다수 클래스만 찍어도 정확도가 높게 나온다. 오늘 실습에서 확인한 숫자로 예를 들면:
- 당뇨 데이터: 무조건 "정상(0)"이라고만 답하는 게으른 모형도 정확도가 꽤 높게 나왔다
- 간호대 합격 데이터: 무조건 "불합격(0)"이라고만 찍어도 정확도 0.663 (전체 250명 중 다수가 불합격이라서)

→ **결론**: 정확도 하나만 보고 "이 모형 괜찮네"라고 판단하면 안 된다. 반드시 클래스 비율(`value_counts(normalize=True)`)을 먼저 확인하고, 정확도를 "게으른 모형"의 정확도와 비교해봐야 한다.

### 2-4. 정밀도(Precision) vs 재현율(Recall) — 그리고 트레이드오프

$$\text{Precision} = \frac{TP}{TP+FP} \qquad \text{Recall} = \frac{TP}{TP+FN}$$

- **정밀도**: 모형이 "양성이다"라고 판정한 것들 중에서, 실제로 양성이었던 비율. "내가 양성이라고 외친 것 중 진짜는 몇 %냐" → 양성 판정의 **신뢰도**
- **재현율**(=민감도, Sensitivity, TPR): 실제로 양성인 것들 중에서, 모형이 놓치지 않고 잡아낸 비율. "진짜 양성 중 몇 %를 찾아냈냐" → **놓치지 않는 능력**

이 둘은 구조적으로 **트레이드오프** 관계다. 임계값을 낮추면(더 쉽게 양성 판정) → 재현율은 올라가지만(놓치는 게 줄어드니까) 정밀도는 내려간다(헛짚는 것도 늘어나니까). 반대도 마찬가지다.

**언제 뭐가 더 중요한지 — 면접에서 자주 묻는 포인트**:
- **암 진단**: 재현율이 훨씬 중요하다. 실제 환자를 "정상"으로 놓치면(FN) 치명적이지만, 정상인을 "의심"으로 한번 더 검사하는 건(FP) 비용은 들어도 생명에는 지장 없다.
- **스팸 필터**: 정밀도가 더 중요하다. 정상 메일을 스팸으로 잘못 걸러내면(FP) 중요한 메일을 놓치는 큰 사고지만, 스팸 몇 개가 받은편지함에 섞이는 건(FN) 불편함 정도다.

### 2-5. 위양성률(Fallout, FPR)과 특이성(Specificity, TNR)

$$\text{FPR} = \frac{FP}{FP+TN} \qquad \text{TNR(특이성)} = \frac{TN}{TN+FP} = 1-\text{FPR}$$

- **위양성률(FPR)**: 실제로 음성인 사람들 중, 잘못해서 양성으로 판정된 비율
- **특이성(TNR)**: 실제로 음성인 사람들 중, 제대로 음성으로 걸러낸 비율

재현율(TPR)이 "양성을 잘 찾는 능력"이라면, 특이성(TNR)은 "음성을 잘 걸러내는 능력"이다. 이 둘이 ROC curve의 두 축이 된다.

### 2-6. F1 점수 — 왜 산술평균이 아니라 조화평균인가

$$F_1 = \frac{2 \times \text{Precision} \times \text{Recall}}{\text{Precision}+\text{Recall}} = \frac{2TP}{2TP+FP+FN}$$

정밀도와 재현율은 트레이드오프 관계라서, 둘 중 하나만 보고 모형을 평가하면 왜곡된다. 그렇다고 산술평균 `(P+R)/2`을 쓰면 문제가 생기는데, 예를 들어 정밀도 1.0, 재현율 0.01이어도 산술평균은 0.5나 나와서 "괜찮아 보이는" 착시가 생긴다.

**조화평균**은 두 값 중 작은 쪽에 훨씬 민감하게 반응한다(극단적으로 작은 값이 하나라도 있으면 전체 평균이 크게 끌려 내려간다). 그래서 정밀도와 재현율 **둘 다 어느 정도 균형 있게 높아야만** F1이 높게 나온다 — "한쪽만 잘해서는 점수를 딸 수 없게" 만드는 게 조화평균을 쓰는 이유다.

### 2-7. ROC curve와 AUC

**ROC curve**: 임계값을 0부터 1까지 쭉 움직여가면서, 매 임계값마다 (FPR, TPR) 좌표를 찍어 이어놓은 곡선이다.
- x축 = 위양성률(FPR, 1-특이성)
- y축 = 재현율(TPR, 민감도)

**대각선(y=x)이 갖는 의미**: 이 선은 "동전 던지기"처럼 완전히 무작위로 찍었을 때 나오는 기준선이다. 임계값을 아무리 움직여도 양성/음성을 구분하는 실질적 정보가 없다면 곡선이 이 대각선에 붙는다.

**AUC(Area Under Curve)**: ROC curve 아래 면적. 특정 임계값 하나가 아니라 **모든 임계값을 통틀어서** 모형의 분류 능력을 요약한 숫자다.
- AUC = 0.5 → 대각선과 같음 → 랜덤 찍기랑 다를 바 없음 (아무것도 학습 못함)
- AUC = 1.0 → 완벽한 분류

오늘 모듈(`report_performance`)에서 쓰인 등급 판정 기준:

| AUC 구간 | 판정 |
|---|---|
| < 0.6 | 모형이 아무것도 학습하지 못함 |
| 0.6 ~ 0.7 | 낮음 |
| 0.7 ~ 0.8 | 쓸 만함 |
| 0.8 ~ 0.9 | 우수 |
| ≥ 0.9 | 매우 우수 |

**`roc_curve()`가 반환하는 `thresholds` 배열이 왜 원본 확률값 개수보다 적은가**: 임계값을 촘촘하게 무한히 움직여도, 실제로 (FPR, TPR) 좌표가 "바뀌는" 지점은 관측된 예측 확률값들이 서로 순서를 뒤바꾸는 지점뿐이다. 그래서 `roc_curve()`는 확률값 하나하나가 아니라, **분류 결과가 실제로 달라지는 지점**만 뽑아서 임계값 후보로 돌려준다. 이게 원본 데이터 개수보다 임계값 개수가 훨씬 적은 이유다.

### 2-8. 진단오즈비(Diagnostic Odds Ratio, DOR)

$$DOR = \frac{TP \times TN}{FP \times FN}$$

지난 시간에 배운 "오즈비(Odds Ratio)"는 회귀계수를 지수변환(`exp(B)`)해서 구했다면, 여기서는 **혼동행렬 네 칸만으로** 같은 개념(오즈의 비율)을 구한다.

말로 풀면: **모형의 판정과 실제 상태가 얼마나 강하게 연결되어 있는가**를 하나의 숫자로 요약한 것이다.
- DOR = 1 → 모형의 판정이 실제 상태와 무관하다 (판정이 의미 없음)
- DOR > 1 → 판정과 실제가 양의 방향으로 연결됨 (클수록 강하게 연결)
- 분모(FP×FN)가 0이면(오분류가 하나도 없으면) 무한대로 취급

오늘 실습에서 확인한 비교: 당뇨 데이터에서는 DOR이 10.13 정도로 나왔는데, 간호대 합격 데이터 연습문제에서는 DOR이 3.582로 나왔다 — 둘 다 "판정이 무의미하지는 않다(1보다 큼)"이지만, **연결의 강도 자체는 당뇨 모형이 훨씬 강하다**는 뜻이다. 이렇게 데이터셋 간에 DOR 크기를 비교하는 감각을 가지면 좋다.

## 3. 두 가지 코딩 버전 — 왜 둘 다 하는가 (모듈 설계 사고방식)

오늘 노트북은 같은 내용을 **두 번** 한다:

**버전 A — 소스에 직접 코딩** (원리 확인용)
```python
y_true = np.asarray(fit.model.endog).astype(int)
proba = np.asarray(fit.predict())
y_pred = (proba > 0.5).astype(int)
cm = confusion_matrix(y_true, y_pred)
tn, fp, fn, tp = cm.ravel()

acc = (tn+tp) / (tn+fp+fn+tp)          # 직접 계산
acc = accuracy_score(y_true, y_pred)    # sklearn 함수로 재확인
```

**버전 B — 모듈 호출** (검증 끝난 뒤 재사용용)
```python
fit = my_logit.auto_logit(origin, 'Outcome', plot=False, report=False)
my_logit.plot_confusion(fit)
my_logit.plot_roc(fit)
my_logit.report_performance(fit)
```

**이 두 버전을 왜 둘 다 짜는가 — 이게 오늘 배운 것 중 가장 중요한 "사고방식"이다:**

1. **먼저 직접 코딩**해서 공식이 뭘 계산하는지, 숫자가 왜 그렇게 나오는지 손으로 확인한다. 이 단계를 건너뛰고 모듈만 쓰면, 모듈이 뭘 하는지도 모른 채 블랙박스로 쓰게 된다 — 나중에 결과가 이상해도 뭐가 잘못됐는지 못 찾는다.
2. **직접 계산값과 sklearn 함수값을 비교**해서 "내가 이해한 공식이 맞다"는 걸 검증한다. (`acc` 두 줄이 같은 값 나오는지 확인하는 게 그 검증이다)
3. 검증이 끝난 로직만 **모듈 함수로 감싸서** 다음 데이터셋에서 재사용한다. `report_performance(fit)` 한 줄로 혼동행렬+6개 지표+AUC등급+DOR+시각화까지 다 나오는 건, 이 로직이 이미 검증됐기 때문에 믿고 쓰는 것이다.

→ 즉, **"처음부터 끝까지 다 손코딩"도 아니고 "처음부터 모듈만 쓰기"도 아니다.** 새로운 개념(혼동행렬)이 나오면 직접 코딩으로 원리를 확인 → 검증되면 모듈에 편입 → 이후로는 모듈만 호출, 이 사이클을 반복하는 게 이 커리큘럼 전체의 패턴이다. 다음에 새로운 통계 개념을 배울 때도 이 순서를 그대로 적용하면 된다.

### 모듈 import 구조 — `from helpers import *`가 뭘 하는가

노트북에서 `from helpers import *` 한 줄만 쓰면 `my_logit.auto_logit(...)`, `my_plot.heatmap(...)` 처럼 **모듈명.함수명** 형태로 바로 쓸 수 있다. 이건 `helpers` 패키지의 `__init__.py`가 내부적으로 `my_logit`, `my_plot`, `my_stats`, `my_qtcheck`, `my_prep`, `my_ols` 같은 서브모듈들을 미리 import해서 노출시켜두고 있기 때문이다. 그래서 노트북 쪽에서는 각 서브모듈을 따로따로 import할 필요 없이 패키지 하나만 불러오면 전부 쓸 수 있는 구조다.

### 4-1. 알려진 버그 (기존에 발견한 것, 이번 파일에도 그대로 있음)

`report_fitness()` 함수 (163~165줄 근처) 유의확률 구간 표기 부분:

```python
if p < 0.001 : alpha = "< 0.001"
elif p < 0.01: alpha = "< 0.01"
elif p < 0.05: alpha - "< 0.05"      # ← 오타! '=' 이 '-' 로 되어있음
else: alpha = ">= 0.05"
```

`=` 대신 `-`가 들어가 있어서, p값이 **[0.01, 0.05) 구간**일 때 `alpha` 변수에 값이 할당되지 않고, 그냥 `alpha - "< 0.05"`라는 실행되지 않는(no-op) 식으로 끝나버린다. 그 뒤에서 `alpha`를 `template.format(alpha=alpha, ...)`에 쓰려는 순간 **`NameError`**가 난다. (완전히 우연히 이전 분기에서 `alpha`가 이미 정의돼 있었다면 그 값이 남아서 틀린 값이 표기될 수도 있다 — 어느 쪽이든 버그다.)

### 4-2. 이상한 자기참조 import (11~13줄)

```python
from . import my_plot 
from . import my_stats
import helpers.my_logit as my_logit    # ← my_logit.py 안에서 자기 자신을 다시 import
```

`my_logit.py` 파일 안에서 `helpers.my_logit`을 또 `my_logit`이라는 이름으로 import하고 있다. 파일 내부 어디에서도 이 `my_logit.` 접두사로 자기 함수를 호출하는 부분은 없어서 지금은 **불필요한 코드(dead code)**로 보인다. 당장 에러를 내지는 않지만(파이썬이 모듈을 캐싱해서 순환 자체는 깨지지 않음), 코드를 읽는 사람 입장에서는 혼란을 준다. 나중에 이 파일을 정리할 기회가 있으면 지워도 되는 줄이다.

## 5. 다른 데이터셋에 적용할 때 체크리스트

1. 종속변수가 정말 0/1 이진값인지 확인 (`data[y].unique()`)
2. `origin[y].value_counts(normalize=True)`로 클래스 비율부터 확인 — 불균형이면 정확도만 보지 않기
3. `fit = my_logit.auto_logit(data, y, plot=False, report=False)` 로 모델만 빠르게 적합
4. "게으른 모형"(다수 클래스만 찍는 모형)의 정확도를 베이스라인으로 계산해두기
5. `my_logit.report_performance(fit)` 한 번 호출로 혼동행렬 + 6개 지표 + AUC + DOR 전부 확인
6. 목적에 따라 임계값 조정 여부 판단 — 재현율이 중요한 문제인지, 정밀도가 중요한 문제인지 먼저 정의
7. 클래스가 심하게 불균형하고 AUC/재현율이 낮게 나오면 "모형 탓"이 아니라 "설명변수가 부족한 것"일 수 있음 — 오늘 연습문제(간호대 합격) 결론이 바로 이거였다 (변수 4개로는 부족, 자기소개서/면접점수 같은 변수 추가 필요)

## 6. 실습(당뇨) vs 연습문제(간호대 합격) 결과 비교

| 지표 | 당뇨(pima) | 간호대 합격 |
|---|---|---|
| 게으른 모형(다수클래스만 찍기) 정확도 | 상대적으로 낮은 편 | 0.663 |
| 재현율(Recall) | 상대적으로 높은 편 | 0.276 (매우 낮음 — 합격자 열 명 중 세 명도 못 찾음) |
| 특이성(Specificity) | - | 0.904 (불합격자는 잘 걸러냄) |
| AUC | - | 0.6904 → "낮음" 등급 |
| 진단오즈비(DOR) | 10.13 | 3.582 |
| 해석 | 판정-실제 연결 강함 | 판정이 다수 범주(불합격) 쪽으로 완전히 쏠린 모형, 설명변수 보강 필요 |

이 비교표가 보여주는 포인트: **같은 코드, 같은 모듈을 써도 데이터 품질(설명변수가 충분한가)에 따라 결과가 완전히 다르게 나온다.** 모듈이 지표를 계산해줄 뿐, 그 지표를 해석하고 "이 모형을 실제로 써도 되는가"를 판단하는 건 분석자 몫이다.

## 7. 복습 체크리스트 (면접 대비 — 말로 설명 가능해야 하는 것들)

- [ ] TN/FP/FN/TP를 "실제-예측" 조합으로 즉시 말할 수 있는가 (예: "FN = 실제 당뇨인데 정상이라고 예측함, 놓친 환자")
- [ ] `cm.ravel()`이 왜 항상 TN,FP,FN,TP 순서인지 (2차원 배열을 row-major로 flatten하기 때문) 설명할 수 있는가
- [ ] 정확도의 함정을 숫자로 설명할 수 있는가 (예: 무조건 0 찍어도 66.3% 나오는 경우)
- [ ] 정밀도 vs 재현율 트레이드오프를 실제 예시(암 진단=재현율, 스팸필터=정밀도)로 바꿔 말할 수 있는가
- [ ] F1이 왜 산술평균이 아니라 조화평균인지 (한쪽만 잘해서는 점수를 딸 수 없게 만들려고) 설명할 수 있는가
- [ ] 임계값을 낮추면 재현율↑ 정밀도↓ 방향을 표 없이 즉석에서 말할 수 있는가
- [ ] FPR=1-특이성, TPR=재현율이라는 것, ROC의 x/y축이 뭔지 바로 말할 수 있는가
- [ ] AUC=0.5가 왜 "랜덤 찍기"와 같은지(대각선의 의미) 설명할 수 있는가
- [ ] `roc_curve()`의 `thresholds` 배열이 원본 확률 개수보다 적은 이유(분류 결과가 실제로 바뀌는 지점만 추출)를 설명할 수 있는가
- [ ] 진단오즈비(DOR)가 지난 시간의 회귀계수 오즈비(exp(B))와 어떻게 다른 방식으로 같은 개념(오즈의 비율)을 구하는지 연결해서 설명할 수 있는가
- [ ] 코드 없이 데이터만 주어졌을 때 "혼동행렬 → 4개 지표 → ROC/AUC"까지 순서대로 손코딩으로 재현할 수 있는가
